## P7 ★ · 核心链路：安全在模型之前

**核心信息**：流程图，突出「预检在模型调用之前」

```
用户输入
   ↓
① 安全预检 ←──── 关键：在模型调用之前
   ↓
  危险？──是──► 拒绝 + 写审计（模型完全不被调用）
   ↓ 否
② 模型规划（国产模型 / 离线规划器）
   ↓
③ 工具白名单 + Schema 校验 + 风险评分
   ↓
  决策？──reject──► 阻断
   │  └─confirm──► dry-run + 一次性令牌人工确认
   ↓ allow
④ SafeExecutor 最小权限执行
   ↓
⑤ 输出安全复检
   ↓
⑥ 跨工具根因分析
   ↓
⑦ 审计写入（request_id 可回放）
```

**讲述要点**：
> 大多数方案是「让模型自己拒绝危险请求」。我们不信这个。**危险输入根本不会被发送给模型**——不给它被诱导的机会。

## P8 ★ · 技术亮点一：跨工具根因分析

**核心信息**：对比图

**逐工具解析（业界常见做法）**

```

**跨工具根因关联（本项目）**
```

                  ↓
  根因链（置信度 0.85）：
  /var 磁盘紧张 → 5 个大文件候选
    ├─ nginx access.log  → 应用日志 → ✅ 可清理
    ├─ nginx error.log   → 应用日志 → ✅ 可清理

**5 个跨工具探测器**：磁盘+大文件 / CPU+进程 / 内存+进程 / 服务+日志 / 磁盘+日志+文件三方交叉

**讲述要点**：
> 差别不在于"能不能列出大文件"，而在于**知道哪些绝对不能碰**。

## P9 ★ · 技术亮点二：关键文件保护（fail-safe）

**核心信息**：四分类决策表

| 分类 | 判定依据 | 可清理 |
| --- | --- | :---: |
| 🔴 数据库文件 | 12 种扩展名 + 15 种路径标识（mysql/postgres/**opengauss**/redis…） | **❌ 自动排除** |
| 🟢 应用日志 | `.log` / `.out` / `.err` / `.nohup` | ✅ |
| 🟢 临时文件 | `/tmp/`、`/var/tmp/`、`/var/cache/` | ✅ |
| 🔴 **归属未知** | 以上都不匹配 | **❌ 默认保护** |

**讲述要点**：
> 最后一行是关键。安全系统的基本原则是 **fail-safe 而不是 fail-open**——不确定就保护，绝不是不确定就删除。

## P10 ★ · 技术亮点三：三个赛题场景全覆盖

| 场景 | 专项工具 | 设计亮点 |
| --- | --- | --- |
| **配置文件漂移** | `config_drift_check` | 纯 Python 标准库采集指纹（不走 Shell，更安全）；10 个关键配置白名单；敏感配置变更定级 critical |
| **僵尸进程堆积** | `zombie_process_check` | 检测 Z 状态 → 定位父进程 → **区分 init 自动 reap vs 服务未回收**，给出技术正确的建议 |
| **磁盘 I/O 异常** | `disk_io_analysis` | 取 `iostat` 第二次采样（稳定值）；util ≥80% **或** await ≥50ms 双阈值；宽松列名映射兼容多版本 |

**讲述要点**（僵尸进程处特别强调）：
> 很多 AI 助手会说"kill 掉僵尸进程"——这是**错的**，僵尸进程已经死了，kill 不掉。必须让父进程 reap 或重启父服务。**给错建议比不给建议更危险**，所以我们把这个判断写死在工具里。

## P13.1 ★★ · 创新一：安全不变式的机器自证明

**核心信息**：全页对比

```
        别人的安全            我们的安全
     ┌──────────────┐    ┌──────────────────┐
     │ "我们有护栏"  │ →  │  10 条不变式      │
     │   （声明）    │    │  机器验证通过     │
     └──────────────┘    └──────────────────┘
```

**5 条静态不变式**（AST 源码结构证明）：

| INV-S1 | subprocess 只允许出现在 SafeExecutor，OS 访问单点收口 |
| INV-S2 | 后端任何位置不得出现 shell=True |
| INV-S3 | 不得使用 os.system / eval / exec 等危险原语 |
| INV-S4 | 工具模块不得直接触达 subprocess |
| INV-S5 | SafeExecutor 必须显式传入 shell=False |

**5 条运行时不变式**（真实请求驱动）：

| INV-R1 | reject 的请求，executed 恒为 false |
| INV-R2 | 每次请求（含被拒绝的）都可回放审计 |
| INV-R3 | 高危输入在**模型调用之前**被拦截 |
| INV-R4 | 三个入口收敛到同一条安全链路 |
| INV-R5 | 伪造/重放令牌不得触发执行 |

**实测**：扫描 51 个文件，subprocess 调用点 **1 处**，静态违规 0，运行时违规 0。

**讲述要点**：
> 验证器同时防守两个方向——既证明危险请求被拒绝，也证明正常请求**没被误拒**。一个"全部拒绝"的护栏能通过前者，通不过后者。失败时非零退出，可以直接当发布门禁用。

## P13.2 ★★ · 创新二：变更 → 故障因果关联

**核心信息**：时间轴图

```
14:20  /etc/ssh/sshd_config 内容漂移（critical）
   │
   │  ← 12 分钟
   ▼
14:32  sshd.service 进入 failed 状态
   │
   ▼
根因（置信度 0.90）：疑似该次配置变更直接导致服务故障
建议：① 比对基线差异 ② 回滚后重启验证 ③ 确认变更来源
```

**双轴对齐**：
- **实体轴**：配置文件 → 所属服务（21 条映射规则）
- **时间轴**：变更检出时间 → 故障时间，1 小时窗口

**防误报**：变更了但服务健康 → 不生成；服务故障但无相关变更 → 不生成。

**讲述要点**：
> 生产环境里绝大多数故障是变更引起的。普通根因分析看的是**当前快照**——能说"sshd 挂了"，答不出"是哪次改动导致的"。这一条把"状态归因"升级成了"变更归因"。

## P13.3 ★★ · 创新三：操作影响面预测

**核心信息**：

```
拟处置 /var/log/nginx/access.log（5.0GB）
├─ 持有句柄：nginx (PID 1234, 1235)
├─ 所属服务：nginx.service
├─ 监听端口：80、443
└─ ⚠ 句柄泄漏风险：直接 rm 后 inode 不释放，磁盘空间不会回收
   建议：truncate 或 logrotate copytruncate，不要 rm
```

**影响面分级**：isolated → service_local → service_impacting → multi_service

**讲述要点**：
> 前一层安全是"别删错文件"，这一层是"删对了也要知道后果"。
>
> 特别是这个句柄泄漏——运维人员 `rm` 掉大日志、发现 `df` 纹丝不动，是极其常见的踩坑。因为文件还被进程持有，inode 不会释放。我们在动手之前就把这个陷阱说清楚。

## P13.4 ★★ · 创新四：自学习基线，取代固定阈值

**核心信息**：两个反例

```
固定阈值 usage >= 85% 的两个致命问题：

主机 A：数据库服务器，常年 90% 内存
  固定阈值 → 天天误报          自学习 → 正常，不报

主机 B：平时 20%，突然升到 60%
  固定阈值 → 完全漏报          自学习 → 立即告警
```

**同一个数字，在不同主机上含义完全不同。**

**方法**：中位数 + MAD（中位绝对偏差）从本机历史学习正常区间。
选择理由：两者对离群值稳健——历史里必然包含要检测的尖峰，用均值/标准差建基线会被尖峰拉高，反而失去检测能力。

**每条告警都能说清依据**：
> CPU 使用率当前 78.0%，高于本机学习基线 3.1% 达 74.9%
> （稳健 z=50.52，正常区间 0.0~18.1%，基于 484 个历史样本）

**讲述要点**：
> 这是把项目里最"笨"的一块换成自适应的。而且告警不是黑盒——基线是多少、偏离多少、基于多少样本，全部摊开给运维核对。

## P13.5 ★ · 定位对照：全权限运维台 vs 最小权限运维台

| 维度 | 全权限运维面板 | SafeOpsAgent |
| --- | --- | --- |
| 运行权限 | root | **普通用户** |
| 命令执行 | 任意 | 白名单 + 单点收口（可静态验证） |
| 写操作 | 直接执行 | dry-run + 一次性令牌确认 |
| 删除能力 | 永久删除 | **不提供**，只做可恢复隔离 |
| 监控能力 | 有 | 有，且阈值自学习 |
| 操作留痕 | 部分 | 全量 append-only，不可清除 |
| 安全性证明 | 无 | **10 条不变式机器验证** |
| 被攻破的后果 | 整机沦陷 | 攻击面限于只读工具集 |

**讲述要点**：
> 我们不是要替代运维面板，是提出另一条路线。这类面板功能全、上手快，但以 root 运行、可任意执行命令——一旦被攻破等于交出整台机器。
>
> **我们想证明的是：运维台的便利性，不必用无限权限来换。**

## P15 ★ · 性能实测

**核心信息**：性能数据表

| 指标 | 实测值 |
| --- | --- |
| 状态接口 P95 | **2.5 ms** |
| 完整诊断链路平均 | **16 ms** |
| **安全预检开销** | **0.15 ms（占整链路 < 1%）** |
| 单进程峰值吞吐 | 94 QPS |
| 并发成功率（1/4/8/16） | **100%，零 5xx** |
| 进程峰值内存 | 68 MB |

**核心结论（放大展示）**：
```
危险请求 13 ms  <  正常请求 16 ms

安全拦截不是额外开销，是抄近路
```

**讲述要点**：
> 很多人担心加了安全层会拖慢系统。我们实测：**安全预检本身只要 0.15 毫秒**，而危险请求因为在预检阶段就被拦截，反而比正常请求更快返回。安全和性能在这里不是取舍关系。

## P17 · 能力边界（主动声明）

**核心信息**：

| 不提供 | 为什么这是设计选择 |
| --- | --- |
| 永久删除文件 | 不可逆操作违背安全可控原则，只提供可恢复隔离 |
| 自动重启 / 自愈 | 写操作处置权保留给管理员，系统只给建议 |
| 内核修改 / eBPF | 超出用户态安全 Agent 定位 |
| 多租户 / RBAC | 产品定位是单机运维 Agent，不是 SaaS 平台 |

**讲述要点**：
> 这一页我们主动放上来。**一个能自动删文件、自动重启服务的运维 Agent，恰恰是不安全的。** 这些边界不是没做完，是刻意不做。

## 附：答辩预设问答

| 评委可能问 | 建议回答 |
| --- | --- |
| **为什么不用模型自己判断危险？** | 模型是概率系统，安全判断需要确定性。我们把 Guardrail 放在模型之前，危险输入根本不发给模型——这样即使模型被越狱，也碰不到系统。 |
| **如果绕过你的 API 直接调工具呢？** | 全后端只有 `SafeExecutor` 一个文件能调 `subprocess.run`，这是静态可验证的。所有入口（HTTP / MCP stdio / MCP SSE）都汇聚到同一条安全链路，没有旁路。 |
| **根因分析准确率如何保证？** | 每条根因链都带置信度和支撑证据列表，证据不足时**不生成**根因链而不是猜一个。18 项测试覆盖了"该生成"和"不该生成"两类情况。 |
| **只支持这几个场景吗？** | 16 个工具可任意组合，`/chat` 支持最多 3 个工具联合诊断。三个专项工具是针对赛题点名场景做的深度优化，通用能力由基础工具矩阵覆盖。 |
| **为什么不做自动修复？** | 这是刻意的设计选择。自动修复意味着系统在无人确认下执行写操作，风险不可控。我们提供 dry-run + 一次性令牌确认 + 可恢复隔离，把决策权留给管理员。 |
| **性能能撑多大规模？** | 单进程实测 94 QPS、并发零错误。瓶颈在审计写入的进程内锁串行化，我们在性能报告里明确写了这一点。多机部署需要替换审计存储后端。 |
| **国产模型适配深度如何？** | 支持 DeepSeek / Qwen / Kimi / 自定义 OpenAI 兼容端点，DeepSeek 已做真实 Key 受控联调验证。模型不可用时自动降级到离线规划器，且降级不放宽任何安全策略。 |
| **为什么不直接用宝塔这类现成面板？** | 那类面板以 root 运行、可任意执行命令，与我们"最小权限、不可绕过"的核心命题直接冲突——建在上面，我们所有的安全论证当场失效。而且它们不支持 LoongArch + 麒麟，会让最硬的适配性证据作废。我们不是替代它，是提出另一条路线。 |
| **自学习基线会不会一开始就误报？** | 不会。样本数不足 12 个时不形成基线、不告警，界面明确显示"学习中"。另外还有最小偏离量下限（CPU 15 个百分点、内存 10 个），避免极稳定指标的微小波动触发空转告警。 |
| **测试为什么有跳过项？** | 6 项跳过：3 项是 Windows 不支持 Unix 特性（软链接、权限位），麒麟上正常执行；3 项是可选 MCP SDK 未安装。我们在报告里逐项说明，不把跳过算作通过。 |
