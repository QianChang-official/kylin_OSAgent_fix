# SafeOpsAgent 创新点说明

**版本**：v1.3.0
**对标赛题评分项**：创新与实用性（25%）

---

## 核心命题

现有的智能运维方案大致分两类，各有一处硬伤：

| 方案 | 硬伤 |
| --- | --- |
| **全权限运维面板**（宝塔类） | 功能全、上手快，但以 root 运行、可任意执行命令。一旦被攻破等于交出整台机器。 |
| **AI 运维助手** | 能理解自然语言，但要么不碰真实系统（只给建议），要么直接开放 Shell（把 root 交给概率模型）。 |

SafeOpsAgent 走第三条路：**最小权限运维台**——提供同等的监控可视化与诊断能力，但任何写操作都必须经过风险评分、dry-run、人工确认与审计留痕。

> 我们要证明的是：**运维台的便利性，不必用无限权限来换。**

围绕这个命题，本版本落地四项创新。

---

## 创新一：安全不变式的机器自证明

### 问题

每一套安全方案都会声称"我们有安全护栏"。但这是**主观声明**，评审者只能选择相信或不相信。当被追问"你怎么证明没有绕过通道"时，通常只能回答"你看代码"。

### 做法

把"安全"从声明变成**一组可判定的属性**，用程序验证。

**静态不变式**（AST 源码结构分析，5 条）：

| 编号 | 不变式 |
| --- | --- |
| INV-S1 | `subprocess.*` 只允许出现在 SafeExecutor，操作系统访问单点收口 |
| INV-S2 | 后端任何位置不得出现 `shell=True` |
| INV-S3 | 不得使用 `os.system` / `os.popen` / `eval` / `exec` 等危险原语 |
| INV-S4 | 工具模块不得直接触达 `subprocess`，必须经由 SafeExecutor |
| INV-S5 | SafeExecutor 中的 `subprocess` 调用必须显式传入 `shell=False` |

**运行时不变式**（真实请求驱动全部入口，5 条）：

| 编号 | 不变式 |
| --- | --- |
| INV-R1 | `security_decision=reject` 的请求，`executed` 恒为 false |
| INV-R2 | 每一次请求（含被拒绝的）都必须产生可回放的审计记录 |
| INV-R3 | 高危输入必须在**模型调用之前**被拦截，而非事后否决 |
| INV-R4 | 所有入口（HTTP `/chat`、`/tools/call`、MCP）收敛到同一条安全链路 |
| INV-R5 | 伪造/重放的确认令牌不得触发执行 |

### 实现

```
backend/security/invariants.py   静态分析器（AST 调用图 + 禁用原语扫描）
scripts/verify_invariants.py     验证器 CLI，输出验证报告
docs/security-invariant-report.md 自动生成的验证报告
```

验证失败时脚本以**非零状态码退出**，可直接作为发布门禁使用。

### 实测结果

```text
扫描文件         : 51
subprocess 调用点: 1（backend/executor/safe_executor.py:51）
静态违规         : 0
运行时违规       : 0
总体结论         : 通过
```

**为什么这是创新**：验证器同时防守两个方向——它不仅证明危险请求被拒绝，也证明正常运维请求**未被误拒**（一个"全部拒绝"的护栏能通过前者但通不过后者）。本科组参赛作品中几乎不会出现形式化验证方向的交付物，而它恰好正面回应评审最可能提出的质疑。

**诚实边界**：这不是形式化数学证明，而是对一组明确列举的可判定属性的验证。报告第 4 节主动写明了它不能证明什么。

## 创新二：变更 → 故障时序因果关联

### 问题

真实生产环境中，**绝大多数故障由变更引起**。但常见的根因分析只看**当前状态快照**——能告诉你"sshd 挂了"，答不出"是哪次改动导致的"。

### 做法

给配置漂移检测加上**时间线持久化**，再在根因引擎中做双轴对齐：

- **实体轴**：变更的配置文件 → 它所配置的服务（`sshd_config` → `sshd`，`my.cnf` → `mysqld`，共 21 条映射）
- **时间轴**：变更检出时间 → 故障发生时间，1 小时窗口内视为强相关

### 输出示例

```
症状：服务异常（sshd）伴随关键配置变更
根因：/etc/ssh/sshd_config 发生配置漂移，且其对应服务 sshd 当前处于异常状态，
      变更在约 12.0 分钟前被检出；疑似该次变更直接导致故障
置信度：0.9
建议：① 比对该文件与基线的差异，确认是否为授权变更
      ② 若为误操作，回滚配置后重启 sshd 验证故障是否消失
      ③ 确认变更来源（人工 / 配置管理工具 / 自动化脚本）以防再次发生
```

### 置信度分级

| 证据组合 | 置信度 |
| --- | --- |
| 服务状态确认异常 + 变更在时间窗内 | 0.90 |
| 服务状态确认异常（时间窗外） | 0.80 |
| 仅日志中出现该服务错误 | 0.65 |

### 防误报设计

- 变更了但服务健康 → **不生成**根因链（变更本身不是故障）
- 服务故障但无相关变更 → **不生成**根因链（不冤枉无关文件）
- 该根因链在结果中**排在通用根因链之前**，因为它是更可操作的结论

**为什么这是创新**：从"状态归因"升级到"变更归因"。运维出身的评审听到这一条会立刻理解其价值——这是排障时最先想问的问题。

**安全一致性**：回滚配置属于写操作，系统只给建议，不自动执行。

## 创新三：操作影响面预测（Blast Radius）

### 问题

系统已经能判断"这个文件能不能删"，但答不出"**删了会影响谁**"。

尤其是一个高频踩坑点：**删除仍被进程持有句柄的日志文件，磁盘空间不会释放**。inode 在进程关闭或重启描述符之前一直存活。运维人员 `rm` 掉大日志、发现 `df` 纹丝不动、然后开始怀疑人生——这是最典型的无效清理。

### 做法

在任何清理决策之前，推演完整影响面：

```
拟处置 /var/log/nginx/access.log（5.0GB）
├─ 持有句柄进程：nginx (PID 1234, 1235)
├─ 所属服务：nginx.service（systemd 托管）
├─ 关联监听端口：80、443
├─ 句柄泄漏风险：是
└─ 建议动作：truncate_or_logrotate
   ⚠ 这是追加写日志，不要直接 rm
     应使用 truncate（`: > 文件`）或配置 logrotate 的 copytruncate，
     让进程继续写入同一 inode，空间才会真正释放
```

### 影响面分级

| 级别 | 条件 | 建议动作 |
| --- | --- | --- |
| `none` | 路径不存在 | 无需处置 |
| `isolated` | 无进程持有 | 可纳入 safe_cleanup_plan 走 dry-run 流程 |
| `service_local` | 被持有且为追加写日志 | **truncate 或 logrotate，不要 rm** |
| `service_impacting` | 被持有且非日志文件 | 人工评估，可能需先停服务 |
| `multi_service` | 被多个服务同时持有 | critical，必须人工介入 |

### 实现

```
backend/tools/impact_tool.py   impact_analysis 工具（只读：lsof + ss + /proc/<pid>/cgroup）
```

**为什么这是创新**：这是"安全"的下一层。前一层是"别删错文件"，这一层是"删对了也要知道后果"。句柄泄漏那条洞察尤其能体现专业度——它是运维实战里非常常见但很少被工具主动提示的陷阱。

## 创新四：自学习基线异常检测 + 监控大盘

### 问题

系统此前用的是**固定阈值**（`usage >= 85%` 判定异常）。这是整个项目里最"不智能"的一块：

- 一台常年跑 90% 内存的数据库服务器，90% 是**正常**的 → 固定阈值天天误报
- 一台平时 20% 的机器突然到 60%，远未到 85% → 固定阈值**完全漏报**

**同一个数字在不同主机上含义完全不同。**

### 做法

让每台主机从**自己的历史**学习正常区间。

**统计方法：中位数 + MAD（中位绝对偏差）**

选择理由：两者都对离群值稳健。历史数据里必然包含我们想检测的尖峰，如果用均值/标准差建基线，基线会被这些尖峰拉高，最终失去检测能力。中位数和 MAD 不会。

**判定规则（两条独立触发）**：

| 触发条件 | 含义 |
| --- | --- |
| `baseline_deviation` | 当前值落在本机学习正常区间之外 |
| `absolute_ceiling` | 超过绝对告警线（无论本机基线如何） |

第二条是必要的补充：一台**整个采样窗口都不健康**的主机，其"正常区间"本身就是病态的，此时只有绝对线能救。

**最小偏离量下限**：MAD 趋近 0 时（极稳定指标），微小变化会让 z 分数爆炸。因此正常区间宽度取「统计带宽」与「最小偏离量」的较大者——CPU 15 个百分点、内存 10 个、磁盘 5 个。这是避免空转告警的关键设计。

### 一个真实发现的缺陷

开发过程中通过实机验证发现：**一个完全稳定的指标（MAD 恰好为 0）永远无法触发告警**。

内存长期精确停在 37% → MAD = 0 → 稳健 z 分数在数学上未定义 → 原先基于 z 阈值的判定条件恒不成立 → **即使内存跳到 91%，也不会告警**。而此时界面上画出的正常区间明明显示 91% 在区间之外。

修正：判定改为**基于区间**而非基于 z 分数。区间宽度已经同时包含统计带宽与最小偏离量下限，在 MAD = 0 时依然良定义，且与界面绘制的区间完全一致。z 分数保留为诊断信息展示。

已补充回归测试 `test_perfectly_stable_metric_still_flags_a_large_jump`。

### 监控大盘

自学习基线需要历史采样，采样数据顺带支撑了完整的监控可视化：

```
后端  backend/monitoring/
      ├─ collector.py  跨平台采集（Linux 读 /proc；Windows 走 Win32 计数器作为开发回退）
      ├─ store.py      SQLite 长表存储，按指标分别执行保留策略
      ├─ baseline.py   中位数 + MAD 学习与判定
      └─ service.py    采样线程（仅由 FastAPI lifespan 启动，导入不产生后台线程）

前端  /console/monitor
      ├─ 主机概览（系统 / 架构 / 核数 / 运行时长 / 采样状态）
      ├─ 指标卡片 × 5，每张含当前值、学习基线、正常区间与趋势曲线
      ├─ 趋势曲线上直接绘出**学习到的正常区间**，越界采样点标红
      └─ 基线偏离告警表，每条列出基线值、偏离量、稳健 z 与完整判定说明
```

**可视化设计**：图表调色板经过校验器验证——序列色 `#3987e5` 在控制台深色背景 `#111820` 上通过明度带、色度下限与 3:1 对比度检查；状态色（good/warning/serious/critical）全部通过对比度检查，且始终与图标 + 文字标签同时出现，绝不单靠颜色传达状态。单序列图表不设图例（标题已说明所绘内容）。

**为什么这是创新**：把项目里最"笨"的固定阈值换成自适应判定，并且**每条告警都能说清判定依据**——"当前 78%，高于本机学习基线 3.1% 达 74.9%，稳健 z=50.52，正常区间 0.0~18.1%，基于 484 个历史样本"。这句话本身就是可核对的证据，而不是一个黑盒告警。

## 与"全权限运维台"的定位对照

| 维度 | 全权限运维面板 | SafeOpsAgent |
| --- | --- | --- |
| 运行权限 | root | **普通用户，不需要 root** |
| 命令执行 | 任意 | 白名单 + 单点收口（可静态验证） |
| 写操作 | 直接执行 | dry-run + 一次性令牌人工确认 |
| 删除能力 | 永久删除 | **不提供**，只做可恢复隔离 |
| 监控能力 | 有 | 有，且阈值自学习 |
| 操作留痕 | 部分 | 全量 append-only，不可清除 |
| 安全性证明 | 无 | **13 条不变式机器验证（5 静态 + 8 运行时）** |
| 被攻破的后果 | 整机沦陷 | 攻击面限于只读工具集 |

**我们不是要替代面板，而是提出另一条路线**：运维台的便利性，不必用无限权限来换。

## 复现方式

```bash
cd safeopsagent
export PYTHONPATH="$(pwd)"

# 创新一：安全不变式验证（失败时非零退出）
python scripts/verify_invariants.py

# 创新四：启动服务后访问监控大盘
export MONITOR_SAMPLE_INTERVAL=2      # 演示用短间隔，默认 60 秒
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
# 浏览器打开 http://127.0.0.1:8000/console/monitor

# 创新二 / 三：随诊断链路自动触发，也可直接调用
curl -X POST http://127.0.0.1:8000/tools/call \
  -H "Content-Type: application/json" \
  -d '{"tool_name":"impact_analysis","arguments":{"path":"/var/log/nginx/access.log"}}'

# 全量测试
python -m pytest -q
```
