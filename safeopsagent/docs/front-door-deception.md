# 前门欺骗与溯源设计

更新时间：2026-07-30

本文说明 SafeOpsAgent 控制台前门的三层结构：**诱饵登录（蜜罐）**、**隐蔽入口门**、**被动溯源取证**，以及它们各自的安全边界。

## 为什么这不是后门

后门的定义是**绕过认证**的隐蔽通道。本设计恰好相反：

| 维度 | 后门 | 本设计 |
| --- | --- | --- |
| 是否绕过认证 | 是 | **否**。隐蔽入口只是让登录表单可达，之后仍须通过 PBKDF2 口令校验。 |
| 是否降低门槛 | 是 | **否**。它增加了一道前置因子，攻击面比单因子登录更小。 |
| 是否可审计 | 否 | **是**。入口门通过/失败、诱饵失败、沙箱会话全部写入审计与证据链。 |
| 是否记录在案 | 否 | **是**。本文即公开设计说明，`INV-R6` 由发布门禁机器验证。 |

一个完全无文档、专门规避审计的隐藏入口在安全评审中就是后门。本设计公开机制、不公开口令——与"公开密码算法、保密密钥"是同一原则。

## 三层结构

```text
公网访问者
  -> /console/login  诱饵登录页（外观与正式登录页一致）
       |
       |-- 提交任意账号密码 --> 恒定失败
       |     连续失败达阈值 --> 发放沙箱会话 --> 合成数据控制台（蜜罐）
       |                                          每一次操作写入证据链
       |
       -- 长按品牌标记 / 盲输口令 + 回车 --> POST /auth/gate
              服务端 PBKDF2 校验口令
                |-- 失败 --> 404（与不存在的路由无法区分）+ 限速 + 记录
                -- 成功 --> 下发短时效门令牌（HttpOnly）
                              |
                              -> 表单就地变为正式登录
                                   -> POST /auth/login 真实口令校验
                                        -> HMAC 签名会话 + CSRF + 审计
```

### 第一层：诱饵登录（蜜罐）

- 配置了入口门后，公开登录页对**任何**凭据都返回失败。
- 连续失败达 `HONEYPOT_TRIGGER_ATTEMPTS`（默认 3）次后，发放**沙箱会话**，客户端会看到一次"登录成功"。
- 沙箱会话渲染的是同一套控制台 UI，但所有数据由 `backend/security/sandbox_plane.py` 凭沙箱会话 ID 确定性生成。同一入侵者多次请求看到的是**同一台**虚构主机，行为自洽。
- 沙箱请求在中间件处被短路应答，**真实处理函数根本不会被调用**。这一隔离由测试 `test_sandbox_session_never_reaches_a_real_handler` 断言：真实的编排器、注册表、审计器、监控服务在沙箱请求期间被替换为抛异常的桩。

### 第二层：隐蔽入口门

- 口令只以 PBKDF2 verifier 形式存在于服务端配置（`CONSOLE_ENTRY_GATE_HASH`），**前端构建产物中不含口令、不含哈希**。
- 前端的隐蔽交互（长按品牌标记、盲输后回车）只负责**呈现一个输入框**，它本身不是秘密，也不承担安全职责。凡是发到浏览器的代码都可被逆向——因此秘密必须在服务端。
- 口令错误返回 `404`，与"该路由不存在"无法区分；未配置入口门时同样返回 `404`，因此也不会暴露"这里有一道门"。
- 入口门与登录各自独立限速，失败的门探测不会挤占运维人员的登录预算。

### 第三层：被动溯源取证

`backend/security/deception.py` 对每一次前门交互记录：

- **来源**：传输层对端地址；仅当对端属于 `CONSOLE_TRUSTED_PROXIES` 时才采信 `X-Forwarded-For`，并自右向左取第一个非代理跳，防止伪造头重置计数或污染证据。
- **指纹**：由客户端自行发送的头部派生的稳定摘要，源地址轮换后仍可关联同一工具。
- **节奏**：请求间隔中位数，用于区分自动化与人工。
- **目标**：尝试过的用户名（保留）、口令的**加盐摘要前缀**（不保留明文）。
- **分类与定级**：`credential_stuffing` / `password_brute_force` / `automated_bruteforce` / `automated_tooling` / `manual_probing`，配合 `low→critical` 严重度。

证据以追加写入的 JSONL 落盘（`data/deception/incidents.jsonl`），超过上限自动轮转。运维人员通过已认证的 `GET /security/deception/incidents` 查看。

## 明确的能力边界

以下是**刻意不做**的，说明理由：

| 未实现 | 理由 |
| --- | --- |
| 主动反制 / 反向扫描攻击者 | 未经授权访问他人系统在多数司法辖区违法，且对代理后的攻击者无效。 |
| 浏览器指纹去匿名化、第三方信标 | 会把访问者数据外发给第三方，违反本项目"默认不外连"的姿态。 |
| 记录攻击者提交的明文口令 | 这些常是从别处复用的**真实**凭据，留存即制造新的泄露责任。仅保留加盐摘要即可支持"同一口令重试"的关联。 |
| 默认开启反向 DNS | 这是唯一的外发查询。默认关闭，使默认姿态零外连、不向被观测方发出任何信号。 |
| 地理/ASN 归属 | 需要离线数据库，项目未附带。可自行接入离线 MMDB 后扩展。 |

**关于"追踪溯源"的诚实说明**：本设计提供的是**被动归因**——记录、关联、定级、留证。它无法确定代理或 Tor 之后的真实身份，任何声称能做到的方案在技术上都不可靠。被动归因的价值在于它经得起复核，可作为事件响应和法律程序的证据基础。

## 珍贵资产保护

`config.PROTECTED_ASSET_PATHS` 在**所有白名单校验之前**生效，覆盖项目目录、`data/`（含审计库与溯源证据）、控制台构建产物。即使有人把清理根误配为项目目录，这些路径也无法进入清理候选。由 `INV-R7` 机器验证。

清理本身仍保持原有约束：仅限临时目录白名单、后缀白名单、最小存留时长、dry-run + 一次性确认 + 元数据复验，且只做**隔离**不做永久删除。

## 机器验证的不变式

| 编号 | 内容 |
| --- | --- |
| INV-R6 | 蜜罐会话在密码学上无法被验证为真实会话，且只能取得合成数据 |
| INV-R7 | 受保护的珍贵资产永远不在自动清理可达范围内 |

沙箱令牌与真实令牌由同一会话密钥派生出的**不同子密钥**签名，并各带 `scope` 声明，两道独立屏障。运行 `python scripts/verify_invariants.py` 验证，失败以非零状态码退出，可直接作为发布门禁。

## 配置

```bash
# 1. 生成运维口令 verifier（登录用）
python scripts/hash_console_password.py

# 2. 生成入口门口令 verifier（隐蔽入口用）
python scripts/hash_console_password.py --entry-gate

# 3. 写入 .env，两者都不要提交到版本库
CONSOLE_AUTH_PASSWORD_HASH=pbkdf2_sha256$600000$...
CONSOLE_ENTRY_GATE_HASH=pbkdf2_sha256$600000$...
CONSOLE_AUTH_SESSION_SECRET=<至少 32 字符随机串>
```

不配置 `CONSOLE_ENTRY_GATE_HASH` 时，入口门与蜜罐均不启用，登录退回熟悉的单因子模式——这也是**运维人员输错密码不会被误关进沙箱**的原因：蜜罐只在诱饵路径上生效，通过入口门之后的登录失败是诚实的 401。

## 演示要点

1. 在登录页连续输入 3 组错误凭据 → 第 3 次"登录成功"，进入蜜罐控制台。
2. 蜜罐中查看监控大盘、调用工具、尝试清除审计 → 全部有响应，全部是假的，审计清除返回 0。
3. 以正式会话访问 `/security/deception/incidents` → 看到刚才那台机器的完整画像：分类、定级、尝试的用户名、口令摘要、节奏、指纹。
4. 长按品牌标记，输入入口门口令 → 表单变为正式登录 → 输入运维账号密码 → 进入真实控制台。
