# ADR-0002：自动执行范围限定为只读，不引入不确定结果对账

状态：已采纳 · 2026-08-01

## 背景

在 Agent 运行时治理这个问题域里，有一类成熟做法是为"结果不确定的写操作"建立
持久化对账账本：调用超时后把结果记为 `UNKNOWN`，用带 CAS 的账本、租约、供应商
身份漂移检测与有序去重投递，保证不会盲目重试导致重复副作用。典型场景是支付调用
超时后重试造成重复扣款。

评估是否要为 SafeOpsAgent 引入同一套机制。

## 决策

**不引入。** SafeOpsAgent 的自动执行范围被限定为只读运维工具，以及不修改文件的
清理扫描/计划；中风险操作走 dry-run 加一次性令牌的人工确认路径。

只读操作不存在"重复执行造成重复副作用"这个问题——重复读一次磁盘用量不会产生
第二笔扣款。为一个不存在的问题引入 CAS 账本、租约过期、重启后漂移检测与 outbox
投递，得到的是复杂度，不是安全性。

## 取而代之做了什么

把力气放在这个项目**真实存在**的那条不确定路径上：中风险确认流程。

- 确认令牌一次性消费，重放同一令牌被拒绝
- 令牌绑定到具体的工具与参数，换参数即失效
- 令牌带过期时间

覆盖在 `backend/tests/test_confirm_flow.py`。

## 后果

- 如果将来放开自动执行范围，允许自动执行有副作用的写操作，**这个决策必须重新
  评估**，因为它的前提届时就不成立了。这是本 ADR 最重要的一句话。
- 现阶段不宣称"exactly-once 副作用"之类的性质。没做的事不写进能力表。

## 为什么把它记下来

不是所有"业界更完整的做法"都该照搬。抄一套与自身执行模型不匹配的机制，产出的
是看起来完备、实际没有对应风险的代码——这本身就是一种"声明强于实现"。把不做的
理由写清楚，比做了不解释更有价值。
