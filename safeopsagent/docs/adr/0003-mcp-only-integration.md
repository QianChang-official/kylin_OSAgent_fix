# ADR-0003：以 MCP 为唯一对外集成面，不做多框架适配层

状态：已采纳 · 2026-08-01

## 背景

Agent 生态里常见的做法是为多个编排框架各写一个适配器，并配一组跨框架
conformance 测试，证明同一套治理语义在每个框架下表现一致。

评估是否要为 SafeOpsAgent 做同类适配。

## 决策

**不做。** 对外集成面只有 MCP（stdio 与 SSE / Streamable HTTP 双传输）。

理由是定位不同：SafeOpsAgent 是一个**完整产品**——自带编排、工具注册表、控制台
与审计，部署在麒麟机上作为运维入口；不是一个嵌进别人 Agent 栈里的库。为它写
六个框架的适配器，在有限时间里只能产出浅示例，而浅示例恰恰是这个项目正在清理
的那类问题：能力表上多一行，背后没有对应深度。

MCP 是标准协议。支持 MCP 的客户端已经能发现并调用全部 17 个工具，这比六个各自
维护的适配器覆盖面更广、维护成本更低。

## 取而代之做了什么

跨框架一致性测试真正验证的是"同一套安全语义不因入口而异"。这个性质在
SafeOpsAgent 里同样存在且更要紧——它有三个入口：HTTP `/chat`、HTTP `/tools/call`、
MCP（两种传输）。

于是把同一个思想落在真实的接口面上：

- **INV-R4**（`scripts/verify_invariants.py`）：三个入口收敛到同一条安全链路，
  同一个高危输入在每个入口都被拒绝
- **`test_audit_gate_entry_points.py`**：审计不可写时，三个入口都拒绝执行，且
  失败模式一致

这比多写五个框架适配器更能证明"治理语义与入口无关"，因为验证的是本项目真实
存在的入口，不是示例代码。

## 后果

- 不支持 MCP 的编排框架需要自行封装 HTTP API。这是明确的取舍，不是遗漏。
- 若将来定位变为"可嵌入库"，本决策需重新评估。
